1. Core Variables, Definitions & Constitutional Separation

This blueprint strictly separates three concepts that are often
conflated:

-   (A) The Reference Index (GFB): A pure mathematical definition of
    global purchasing power.

-   (B) The Monetary Unit (MTQ Σ): A token representing a claim to one
    GFB-Unit.

-   (C) The Reserve Portfolio (Collateral): Assets held to back that
    obligation.

Rule: The Index defines the value. The Reserve backs the token. The
token is a liability, not an index itself.

2. The Formal GFB Index Mathematical Specification

2.1 Fixed Currency Quantities (The Basket)

To provide an unambiguous, reproducible monetary anchor, the GFB Index
is constructed using fixed notional quantities of five major currencies,
exactly as the IMF SDR basket is constructed.

Base Date: January 1, 2026, 00:00 UTC (the genesis timestamp).
Calibration Objective: Set the initial quantities qiqi​ so
that GFBbase=1.0000GFBbase​=1.0000 (i.e., the index starts at exactly
1.00 USD‑equivalent).

2.1.1 The Fixed Quantity Table

These quantities are immutable except by constitutional governance
(7‑of‑7 Multi‑Sig, 90‑day timelock). They define the basket size per 1
MTQ unit.

Critical Implementation Rule:
The quantities qiqi​ are expressed in USD‑equivalent units at the base
date.
For example: qEUR=0.2780qEUR​=0.2780 means the basket contains a fixed
amount of EUR that was worth $0.2780 on the base date. This is
a fixed‑quantity basket; weights will drift naturally as FX rates move.

To ensure the index starts at exactly 1.0000, we divide the current

Where:

3. MTQ Reference Price & Liability (The Monetary Unit)

This section defines the USD‑equivalent value of 1 MTQ Σ at any moment,
and the total USD‑denominated liability that the reserve must
collateralise.

It establishes the core relationship that enforces the “Not a Dollar”
principle: the price of MTQ moves with the GFB Index, not with a fixed
1:1 USD peg.

3.1 The MTQ Reference Price Formula

The Reference Price of 1 MTQ Σ at time tt is defined as the normalised
GFB Index value.

PMTQ,t=GFBtGFBbasePMTQ,t​=GFBbase​GFBt​​

Where:

-   GFBtGFBt​ = Current GFB Index value (USD‑equivalent, as defined in
    §2).

-   GFBbaseGFBbase​ = GFB Index value at the Genesis Date (January 1,
    2026, 00:00 UTC).

Interpretation:

-   If GFBt=1.12GFBt​=1.12, then 1 MTQ=$1.121 MTQ=$1.12.

-   If GFBt=0.92GFBt​=0.92, then 1 MTQ=$0.921 MTQ=$0.92.

-   If GFBt=1.00GFBt​=1.00, then 1 MTQ=$1.001 MTQ=$1.00.

Constitutional Invariant: The contract does not contain any function to
set PMTQ,tPMTQ,t​ directly. The price is entirely derived from the
on‑chain oracle data via the GFB formula. This prevents any manual
manipulation of the token price.

3.2 The Liability (USD‑Denominated Collateral Requirement)

The total liability of the protocol is the total USD value of all
circulating MTQ Σ tokens.

Lt=Scirc,t×PMTQ,tLt​=Scirc,t​×PMTQ,t​

Where:

-   Scirc,tScirc,t​ = Circulating Supply of MTQ Σ (tokens held by users,
    excluding the Genesis Reserve Account and protocol‑owned locked
    balances).

-   PMTQ,tPMTQ,t​ = The MTQ Reference Price (from §3.1).

Critical Distinction — Total Supply vs. Circulating Supply:

-   totalSupply() (ERC‑20) includes the Genesis Reserve locked in the
    protocol vault.

-   circulatingSupply is used for liability calculations. The Genesis
    Reserve is a protocol asset, not a user liability. It is excluded
    from Scirc,tScirc,t​ to prevent the protocol from collateralising its
    own locked tokens.

The Liability Check: The Reserve Ratio is computed as:

RRt=Vnet,tLtRRt​=Lt​Vnet,t​​

This means the reserve must always be at least 1.10×Lt1.10×Lt​ (110%
collateralised).

4. Reserve NAV, Collateralization & Liquidity Coverage

This section defines how the protocol measures the actual value of its
reserve, how it calculates the collateral buffer, and how it
ensures immediate liquidity to meet redemption requests.

It establishes the three core health metrics:

-   NAV (Net Asset Value): The prudential value of all reserve assets
    after applying safety haircuts.

-   RR (Reserve Ratio): The solvency buffer (target 110%).

-   LCR (Liquidity Coverage Ratio): The short-term liquidity buffer
    (target ≥ 100%).

4.1 Net Asset Value (NAV) — Prudential Reserve Valuation

The protocol does not use the gross market value of assets to determine
solvency. Instead, it applies a haircut to each asset class to account
for settlement risk, custody risk, and potential depeg or slippage
during liquidation.

Vnet,t=∑j=1n(Qj,t×Pj,t×(1−Hj))Vnet,t​=j=1∑n​(Qj,t​×Pj,t​×(1−Hj​))

Where:

-   Qj,tQj,t​ = Quantity of reserve asset jj (e.g., 10,000 USDC, 1.5
    PAXG).

-   Pj,tPj,t​ = Current USD price of asset jj (from the Oracle consensus,
    §9).

-   HjHj​ = Fixed haircut (safety discount) for asset jj.

Note on Gold: The protocol uses the more conservative of the two gold
prices for NAV calculation:

-   Pgold,referencePgold,reference​ (LBMA spot)
    vs Pgold,executablePgold,executable​ (PAXG market price).

-   Pj,t=min⁡(Preference,Pexecutable)Pj,t​=min(Preference​,Pexecutable​) to
    avoid overvaluing gold during thin liquidity.

4.3 Liquidity Coverage Ratio (LCR)

Solvency (RR ≥ 100%) does not guarantee liquidity. A vault can be fully
solvent but hold assets that cannot be sold quickly enough to meet a
sudden surge in redemptions. The LCR addresses this.

LCRt=Liquid AssetstStress Redemption DemandtLCRt​=Stress Redemption Demandt​Liquid Assetst​​

4.3.1 Definition of Liquid Assets

Liquid Assets are defined as the portion of the reserve that can be
settled within 24 hours without incurring excessive slippage (> 0.5%).

-   Stablecoins (USDC, EURC, etc.) are considered 100% liquid.

-   Tokenized Gold (PAXG) is considered 0% liquid for LCR purposes (gold
    markets can be closed on weekends; DEX liquidity can evaporate).

-   BUIDL / Tokenized T‑Bills are considered 0% liquid unless explicitly
    approved by the Risk Council.

Formula:

Liquid Assetst=∑j∈StablecoinsQj,t×Pj,t×(1−Hj)Liquid Assetst​=j∈Stablecoins∑​Qj,t​×Pj,t​×(1−Hj​)

4.3.2 Definition of Stress Redemption Demand

The Stress Redemption Demand is the estimated total USD value that could
be redeemed within a 30‑day stress period.

Stress Redemption Demandt=Scirc,t×PMTQ,t×0.25Stress Redemption Demandt​=Scirc,t​×PMTQ,t​×0.25

Assumption: Under extreme market conditions, up to 25% of the
circulating supply could be redeemed within 30 days. This is a
conservative assumption based on historical stablecoin depeg scenarios.

4.3.3 LCR Constitutional Floor

LCRt≥1.00LCRt​≥1.00

If LCRt<1.00LCRt​<1.00:

-   The protocol enters DEFENSIVE mode.

-   Rebalancing is re‑routed to increase the liquid asset
    allocation (sell gold for stablecoins) until LCR returns above 1.00.

-   Minting is paused until LCR recovers.

5. Asset Admission Registry (Eligible Reserve Assets)

5.1 Purpose

The Asset Admission Registry is the canonical source of truth for which
on‑chain assets are eligible to be held in the Reserve Vault. It
decouples the reference index (currencies) from the implementation
assets (stablecoins, gold tokens, etc.), allowing the protocol to adapt
to changes in the stablecoin ecosystem without rebuilding the core
monetary logic.

The registry is used by:

-   The Minting Engine to know which assets to buy when a user deposits

-   The Rebalancing Engine to know which assets are eligible for

5.6 Concentration Limits

To prevent over‑reliance on a single issuer (e.g., Circle), the protocol
enforces:

Value of assets issued by issueriTotal Reserve Value≤30%Total Reserve ValueValue of assets issued by issueri​​≤30%

Enforcement: The Rebalancing Engine (§7) checks this constraint before
executing any trade that would increase exposure to an issuer that
already exceeds 25% of the reserve. If a trade would breach 30%, it is
blocked.

Governance Override: A 4‑of‑7 Risk Council vote can temporarily raise
the limit to 35% during a liquidity crisis, but this requires a 24h
timelock and public disclosure.

5.7 Chain Diversification Policy

To minimise blockchain‑specific risk (e.g., L2 downtime, bridge
exploits), the protocol follows these rules:

-   Primary Chain: The Reserve Vault holds assets only on the mainnet of
    the deployed chain (e.g., Arbitrum, Ethereum).

-   No Wrapped Assets: The protocol does not hold wrapped versions of
    assets that are native to another chain (e.g., wormhole USDC). Only
    the native token (e.g., native USDC on Arbitrum) is allowed.

-   Canonical Token Preference: For each asset, the Asset Admission
    Registry must specify the canonical token address for the deployed
    chain. The protocol does not accept alternative bridges.

-   Chain‑Specific Risk: If the Risk Council determines that the
    deployed chain poses elevated risk (e.g., repeated sequencer
    failures), it may pause minting and rebalancing until the issue is
    resolved.

6. The Adaptive Macro Engine (Regime Detection)

6.1 Purpose

The Adaptive Macro Engine detects changes in global market conditions
and adjusts the target gold weight of the reserve portfolio accordingly.
This ensures the protocol is:

-   More defensive during high‑volatility or dollar‑strength regimes
    (increasing gold allocation).

-   More neutral during stable, low‑volatility regimes (reverting to the
    base allocation).

The engine is non‑discretionary: it uses objective, on‑chain observable
data (VIX and DXY) transformed into standardized z‑scores. There is no
human subjectivity in the adjustment.

6.2 Input Signals (On‑Chain Oracle Data)

The engine uses two primary market signals:

  ----------------------------------------------------------------------------------
  Signal   Symbol     Source      Description
  -------- ---------- ----------- --------------------------------------------------
  VIX      VIXtVIXt​   Chainlink / CBOE Volatility Index (market fear gauge). Higher
                      Pyth        values indicate stress.

  DXY      DXYtDXYt​   Chainlink / US Dollar Index (strength of USD against a basket
                      Pyth        of major currencies). Higher values indicate
                                  dollar strength.
  ----------------------------------------------------------------------------------

Frequency: Both signals are updated every 60 seconds via the oracle
architecture (§9). The engine uses the latest validated prices.

Fallback: If either feed is stale or unavailable, the engine uses
the last known good value and flags a WATCH status. If both feeds are
unavailable for > 5 minutes, the engine freezes the target weight at its
last computed value and triggers PAUSE_REBALANCE.

6.3 Standardized Signals (Z‑Scores)

To make the two signals economically comparable, the engine transforms
them into standardized z‑scores using rolling 90‑day means and standard
deviations.

6.3.1 Rolling Statistics

μVIX,t=190∑i=089VIXt−iμVIX,t​=901​i=0∑89​VIXt−i​σVIX,t=189∑i=089(VIXt−i−μVIX,t)2σVIX,t​=891​i=0∑89​(VIXt−i​−μVIX,t​)2​

Similarly for DXY.

Note: The rolling window is 90 calendar days (~66 trading days) to
capture medium‑term market regimes while smoothing out daily noise.

6.3.2 Z‑Score Calculation

ztVIX=VIXt−μVIX,tσVIX,t+ϵztVIX​=σVIX,t​+ϵVIXt​−μVIX,t​​ztDXY=DXYt−μDXY,tσDXY,t+ϵztDXY​=σDXY,t​+ϵDXYt​−μDXY,t​​

Where ϵ=10−9ϵ=10−9 prevents division by zero.

Interpretation:

-   z=0z=0 → Signal is at its 90‑day average (neutral).

-   z=+2z=+2 → Signal is two standard deviations above average (extreme
    stress / strong dollar).

-   z=−2z=−2 → Signal is two standard deviations below average (calm /
    weak dollar).

6.4 The Gold Weight Adjustment

The adjustment to the target gold weight is a linear combination of the
two standardized signals, capped to prevent extreme allocation shifts.

θt=clip(α⋅ztVIX+β⋅ztDXY,−θmax,+θmax)θt​=clip(α⋅ztVIX​+β⋅ztDXY​,−θmax​,+θmax​)

Where:

-   α=0.15α=0.15 — Sensitivity to volatility (VIX).

-   β=0.10β=0.10 — Sensitivity to dollar strength (DXY).

-   θmax=0.03θmax​=0.03 — Maximum shift of ±3 percentage points from the
    base weight.

Rationale for Coefficients:

-   VIX is more directly linked to gold demand (flight to safety), so it
    receives a higher weight (0.15 vs 0.10).

-   The caps prevent the gold weight from moving more than ±3% in a
    single adjustment cycle, ensuring stability.

6.5 The Dynamic Target Gold Weight

The base target gold weight
is Wgoldbase=0.2625Wgoldbase​=0.2625 (26.25%), derived from the portfolio
optimisation in §4.

Wgold,ttarget=Wgoldbase+θtWgold,ttarget​=Wgoldbase​+θt​Wfiat,ttarget=1−Wgold,ttargetWfiat,ttarget​=1−Wgold,ttarget​

Constitutional Constraint: The target gold weight is bounded to prevent
extreme allocations:

0.22≤Wgold,ttarget≤0.300.22≤Wgold,ttarget​≤0.30

-   Lower Bound (22%): Ensures the protocol maintains a minimum gold
    hedge even during extreme calm.

-   Upper Bound (30%): Prevents over‑exposure to gold volatility.

Enforcement: If the computed target exceeds these bounds, it is clamped
to the bound. This is a hard constraint, not a recommendation.

6.6 Smoothing (Anti‑Oscillation)

To prevent the target weight from changing too rapidly (which would
cause frequent, costly rebalancing), the engine applies an exponential
moving average (EMA) to the target weight:

Wgold,tsmoothed=λ⋅Wgold,ttarget+(1−λ)⋅Wgold,t−1smoothedWgold,tsmoothed​=λ⋅Wgold,ttarget​+(1−λ)⋅Wgold,t−1smoothed​

Where:

-   λ=0.20λ=0.20 — Smoothing factor (20% weight to the new target, 80%
    to the previous smoothed value).

-   Result: The target weight changes gradually over ~5‑7 days, avoiding
    whipsaw rebalancing.

Implementation Note: The smoothing is applied off‑chain in the keeper
bot, or on‑chain via a state variable updated daily. The contract
exposes the raw target and the smoothed target separately for
transparency.

6.7.2 Core Logic

solidity

/**

* @dev Updates the rolling history with the latest VIX and DXY values.

* Called by the keeper bot every hour (or via `update()` function).

*/

function updateSignals(uint256 vix, uint256 dxy) external {

// Validate inputs (must be within plausible range)

require(vix >= 10e18 && vix <= 80e18, "VIX out of range");

require(dxy >= 80e18 && dxy <= 120e18, "DXY out of range");

// Store in rolling history

vixHistory[historyIndex] = vix;

dxyHistory[historyIndex] = dxy;

historyIndex = (historyIndex + 1) % WINDOW_DAYS;

lastVIX = vix;

lastDXY = dxy;

lastUpdateTime = block.timestamp;

// Compute new target weight

uint256 newTarget = computeTargetGoldWeight();

uint256 smoothed = smoothTarget(newTarget);

lastSmoothedGoldWeight = smoothed;

emit SignalsUpdated(vix, dxy, newTarget, smoothed);

}

/**

* @dev Computes the target gold weight based on current signals.

* Returns the raw target (before smoothing) in 1e18 scale.

*/

function computeTargetGoldWeight() public view returns (uint256) {

// Calculate rolling mean and std dev for VIX

(uint256 meanVIX, uint256 stdVIX) = calculateRollingStats(vixHistory);

// Calculate rolling mean and std dev for DXY

(uint256 meanDXY, uint256 stdDXY) = calculateRollingStats(dxyHistory);

// Z‑scores (avoid division by zero)

uint256 zVIX = (stdVIX > 0) ? (lastVIX - meanVIX) * 1e18 / stdVIX : 0;

uint256 zDXY = (stdDXY > 0) ? (lastDXY - meanDXY) * 1e18 / stdDXY : 0;

// Adjustment theta

uint256 theta = (ALPHA * zVIX / 1e18) + (BETA * zDXY / 1e18);

// Clamp theta to [-THETA_MAX, +THETA_MAX]

if (theta > THETA_MAX) theta = THETA_MAX;

if (theta < -THETA_MAX) theta = -THETA_MAX; // Note: need signed integer
handling

// Target weight = base + theta

uint256 target = BASE_GOLD_WEIGHT + theta;

// Clamp to [22%, 30%]

if (target > 0.30e18) target = 0.30e18;

if (target < 0.22e18) target = 0.22e18;

return target;

}

/**

* @dev Applies EMA smoothing to the target weight.

*/

function smoothTarget(uint256 newTarget) public view returns (uint256) {

uint256 previous = lastSmoothedGoldWeight;

if (previous == 0) return newTarget; // First update

return (SMOOTHING_LAMBDA * newTarget / 1e18) + ((1e18 -
SMOOTHING_LAMBDA) * previous / 1e18);

}

/**

* @dev Calculates rolling mean and standard deviation.

*/

function calculateRollingStats(uint256[WINDOW_DAYS] storage history)
internal view returns (uint256 mean, uint256 stdDev) {

uint256 sum = 0;

uint256 count = 0;

for (uint256 i = 0; i < WINDOW_DAYS; i++) {

if (history[i] > 0) {

sum += history[i];

count++;

}

}

if (count == 0) return (0, 0);

mean = sum / count;

uint256 variance = 0;

for (uint256 i = 0; i < WINDOW_DAYS; i++) {

if (history[i] > 0) {

uint256 diff = history[i] > mean ? history[i] - mean : mean -
history[i];

variance += (diff * diff) / count;

}

}

stdDev = sqrt(variance);

return (mean, stdDev);

}

/**

* @dev Simple integer square root (Babylonian method).

*/

function sqrt(uint256 x) internal pure returns (uint256) {

if (x == 0) return 0;

uint256 z = (x + 1) / 2;

uint256 y = x;

while (z < y) {

y = z;

z = (x / z + z) / 2;

}

return y;

}

7. The Rebalancing Engine (Dynamic Optimization)

7.1 Purpose

The Rebalancing Engine is the execution layer of the monetary policy. It
monitors the reserve portfolio, compares it against the target weights
(from Section 6), and executes trades to bring the portfolio back into
alignment.

Unlike a fixed‑threshold system, this engine uses a dynamic,
cost‑sensitive decision process. It only rebalances when the expected
benefit of reducing deviation exceeds the estimated cost of execution
(gas, slippage, and market impact). This minimises unnecessary churn and
preserves the protocol's operational surplus.

Key Features:

-   Dynamic Threshold: The trigger adapts to market volatility and
    liquidity.

-   Cost‑Benefit Optimisation: Trades are sized to maximise net benefit.

-   Liquidity‑Aware Sizing: Trade sizes are capped by pool depth to
    avoid slippage.

-   Direction Lock (Whipsaw Guard): Prevents immediate reversal of
    trades to avoid gas waste.

The engine executes a rebalance if and only if the marginal benefit of

applies the pool‑specific slippage curve, and computes the net benefit.

worth the gas and slippage), the trade is executed.

7.5 Trade Sizing (Liquidity‑Sensitive)

To avoid moving the market against itself, the trade size is dynamically
capped by the available pool depth:

TradeSizemax=min⁡(∣Δt∣×Vnet,t, 0.10×PoolDepth24h)TradeSizemax​=min(∣Δt​∣×Vnet,t​, 0.10×PoolDepth24h​)

-   The 10% cap ensures the protocol never consumes more than 10% of the

    slippage.

staged trades over several days (spreading the execution cost).

7.6 Execution Constraints

7.6.1 Slippage Guard

All trades are executed via a DEX aggregator (1inch, Paraswap)
with both‑sided slippage protection:

-   When Selling Gold:

ExecRate≥OracleRate×(1−τ)ExecRate≥OracleRate×(1−τ)

-   When Buying Gold:

ExecRate≤OracleRate×(1+τ)ExecRate≤OracleRate×(1+τ)

Where τ=0.01τ=0.01 (1%, adjustable by the Risk Council).

7.6.2 Maximum Daily Turnover

To prevent excessive trading, the engine enforces a maximum daily
turnover of 5% of the total reserve value. If the required rebalance
exceeds this, the remaining amount is deferred to the next day.

7.6.3 Direction Lock (Whipsaw Guard)

To prevent oscillation (selling gold one day, buying it back the next),
the engine implements a 24‑hour direction lock:

-   If the engine sold gold in the last 24 hours, it cannot sell gold
    again (but it can buy gold if the deviation reverses direction).

-   If the engine bought gold in the last 24 hours, it cannot buy gold
    again (but it can sell gold).

Exception: The direction lock is overridden if the Reserve Ratio drops
below 1.05 (Stress Mode). In that case, the engine may reverse direction
regardless of the lock to protect solvency.

7.7 Integration with the Adaptive Macro Engine

The Rebalancing Engine uses the smoothed target gold weight from Section
6 as its primary reference.

Flow:

4.  The trade is executed through the DEX aggregator.

Note: The engine recalculates the target every time it evaluates a
rebalance. If the target changed since the last evaluation, the engine
adapts immediately.

/**

* @dev Evaluates whether a rebalance is needed and executes it if
profitable.

* Called by the keeper bot (or via `executeRebalance()` function).

*/

function executeRebalance() external {

// 1. Update state

updateReserveState(); // From §4.4.2

uint256 nav = getNAV();

uint256 rr = getReserveRatio();

uint256 targetGold = getTargetGoldWeight(); // From §6.7

// 2. Compute observed gold weight

uint256 goldValue = reserveState.goldValue;

uint256 observedGold = (goldValue * 1e18) / nav;

// 3. Compute deviation

int256 deviation = int256(observedGold) - int256(targetGold);

if (deviation == 0) return; // Perfectly balanced

// 4. Direction lock check (except in stress mode)

if (rr >= 1.05e18) {

if (block.timestamp - lastTrade.timestamp < DIRECTION_LOCK_DURATION) {

if ((deviation > 0 && lastTrade.direction == -1) ||

(deviation < 0 && lastTrade.direction == 1)) {

return; // Locked in same direction

}

}

}

// 5. Compute optimal trade size (simplified: use the deviation)

uint256 surplusValue = abs(deviation) * nav / 1e18;

// 6. Cap by liquidity

uint256 poolDepth = getPoolDepth(PAXG_USDC_POOL);

uint256 maxTrade = (poolDepth * MAX_POOL_FRACTION) / 1e18;

if (surplusValue > maxTrade) surplusValue = maxTrade;

// 7. Cap by daily turnover

resetDailyTurnover();

if (surplusValue > (nav * MAX_DAILY_TURNOVER / 1e18) - dailyTurnover) {

surplusValue = (nav * MAX_DAILY_TURNOVER / 1e18) - dailyTurnover;

}

// 8. Estimate costs

uint256 estimatedCost = estimateExecutionCost(surplusValue, deviation >
0);

uint256 urgency = (rr < 1.10e18) ? (1e18 / rr) : 0;

// 9. Compute net benefit (objective function improvement)

uint256 currentDeviation = abs(deviation);

uint256 newDeviation = abs(deviation - (int256(surplusValue) * 1e18 /
int256(nav)));

uint256 benefit = (currentDeviation - newDeviation) * LAMBDA_1 / 1e18;

benefit += urgency * LAMBDA_3 / 1e18;

uint256 costTerm = estimatedCost * LAMBDA_2 / 1e18;

// 10. Execute if beneficial

if (benefit > costTerm) {

// Execute the trade

if (deviation > 0) {

// Sell gold

uint256 sellAmount = (surplusValue * 1e18) / getGoldPrice();

sellGold(sellAmount);

lastTrade.direction = -1;

} else {

// Buy gold

uint256 buyAmount = (surplusValue * 1e18) / getGoldPrice();

buyGold(buyAmount);

lastTrade.direction = 1;

}

lastTrade.timestamp = block.timestamp;

dailyTurnover += surplusValue;

emit RebalanceExecuted(block.timestamp, deviation, surplusValue,
estimatedCost);

}

}

uint256 gas = 50e18; // $50 in wei (simplified)

/**

* @dev Updates the buffer state based on the current Reserve Ratio.

* Called after every mint, redeem, rebalance, or price update.

*/

function updateBufferState() internal {

uint256 rr = getReserveRatio(); // From §4.4.3

BufferState newState;

if (rr >= RR_BASE_THRESHOLD) {

newState = BufferState.BASE;

} else if (rr >= RR_STRESS_THRESHOLD) {

newState = BufferState.STRESS;

} else {

newState = BufferState.EMERGENCY;

}

// Handle state transitions

if (newState != currentBufferState) {

if (newState == BufferState.EMERGENCY) {

// Immediate transition to EMERGENCY

currentBufferState = newState;

rampStartTime = 0; // No ramp for emergency

emit BufferStateChanged(newState, "EMERGENCY", block.timestamp);

// Pause minting

pauseMinting();

// Trigger emergency rebalance (force gold target to 30%)

triggerEmergencyRebalance();

} else {

// Ramp between BASE and STRESS

rampStartTime = block.timestamp;

rampStartGoldRatio = getCurrentBufferGoldRatio();

rampTargetGoldRatio = (newState == BufferState.BASE) ? BUFFER_GOLD_BASE
: BUFFER_GOLD_STRESS;

currentBufferState = newState;

emit BufferStateChanged(newState, "RAMPING", block.timestamp);

}

}

}

/**

* @dev Returns the current buffer gold ratio (considering ramps).

*/

function getCurrentBufferGoldRatio() public view returns (uint256) {

if (currentBufferState == BufferState.EMERGENCY) {

return BUFFER_GOLD_EMERGENCY;

}

if (rampStartTime == 0) {

return (currentBufferState == BufferState.BASE) ? BUFFER_GOLD_BASE :
BUFFER_GOLD_STRESS;

}

// Check if ramp is complete

if (block.timestamp >= rampStartTime + RAMP_DURATION) {

return rampTargetGoldRatio;

}

// Compute progress (0 to 1)

uint256 elapsed = block.timestamp - rampStartTime;

uint256 progress = (elapsed * 1e18) / RAMP_DURATION;

// Interpolate

uint256 diff = (rampTargetGoldRatio > rampStartGoldRatio) ?

rampTargetGoldRatio - rampStartGoldRatio :

rampStartGoldRatio - rampTargetGoldRatio;

uint256 adjustment = (diff * progress) / 1e18;

return (rampTargetGoldRatio > rampStartGoldRatio) ?

rampStartGoldRatio + adjustment :

rampStartGoldRatio - adjustment;

}

/**

* @dev Returns the total target gold weight (core + buffer).

* This is the value used by the Rebalancing Engine (§7).

*/

function getTotalTargetGoldWeight() public view returns (uint256) {

uint256 bufferGoldRatio = getCurrentBufferGoldRatio();

return CORE_GOLD_WEIGHT + (BUFFER_SIZE * bufferGoldRatio / 1e18);

}

/**

* @dev Returns the total target fiat weight.

*/

return 1e18 - getTotalTargetGoldWeight();

}

/**

* @dev Applies a loss to the buffer using the first‑loss waterfall.

* Called when a loss is detected (e.g., stablecoin depeg, oracle
correction).

*/

function applyLoss(uint256 lossAmount) internal {

uint256 remainingLoss = lossAmount;

// 1. Consume operational surplus (fee revenue)

uint256 surplus = getOperationalSurplus();

if (surplus > 0) {

uint256 consumed = (surplus >= remainingLoss) ? remainingLoss : surplus;

remainingLoss -= consumed;

consumeSurplus(consumed);

if (remainingLoss == 0) return;

}

// 2. Consume buffer fiat

uint256 bufferFiat = getBufferFiatValue();

if (bufferFiat > 0) {

uint256 consumed = (bufferFiat >= remainingLoss) ? remainingLoss :
bufferFiat;

remainingLoss -= consumed;

consumeBufferFiat(consumed);

if (remainingLoss == 0) return;

}

// 3. Consume buffer gold

uint256 bufferGold = getBufferGoldValue();

if (bufferGold > 0) {

uint256 consumed = (bufferGold >= remainingLoss) ? remainingLoss :
bufferGold;

remainingLoss -= consumed;

consumeBufferGold(consumed);

if (remainingLoss == 0) return;

}

// 4. Consume core fiat (emergency)

uint256 coreFiat = getCoreFiatValue();

if (coreFiat > 0) {

uint256 consumed = (coreFiat >= remainingLoss) ? remainingLoss :
coreFiat;

remainingLoss -= consumed;

consumeCoreFiat(consumed);

if (remainingLoss == 0) return;

}

// 5. Consume core gold (requires governance approval)

if (remainingLoss > 0) {

requireGovernanceApprovalForCoreGoldConsumption(remainingLoss);

consumeCoreGold(remainingLoss);

}

}

9. Oracle Architecture (Multi-Source, Timestamp & Confidence)

9.1 Price Fetching & Validation

For each asset, the contract queries three sources:

1.  Chainlink (Primary).

2.  Pyth Network (High-frequency).

3.  Chronicle Protocol (Verifiable).

9.2 The Validation Criteria

The contract does not simply take the median. It applies:

1.  Timestamp: Only prices updated within the last 60 seconds are valid.

2.  Staleness Threshold: If a feed is stale, it is discarded.

3.  Confidence Interval: The confidence interval width must be < 1% of
    the price.

4.  Deviation: Any feed deviating by > 2.5% from the median is discarded
    (not 5%, as PAXG can be more volatile).

9.3 Median with Confidence Weighting

If all three feeds are valid:

Pfinal=Median(P1,P2,P3)Pfinal​=Median(P1​,P2​,P3​)

If only two are valid, use the average. If fewer than two, pause minting
and rebalancing.

10. Execution & Slippage Protection (Two-Sided Bounds)

10.1 The Quote-Based Execution (No Spot Assumption)

Before executing a swap, the contract fetches a route quote from the
aggregator (1inch/Paraswap).

10.2 Two-Sided Slippage Bounds

For Selling Gold (PAXG → USDC):

Exec_Rate≥Oracle_Rate×(1−τ)Exec_Rate≥Oracle_Rate×(1−τ)

For Buying Gold (USDC → PAXG):

Exec_Rate≤Oracle_Rate×(1+τ)Exec_Rate≤Oracle_Rate×(1+τ)

Where τ=0.01τ=0.01 (1% tolerance, adjustable by governance).

Failure Condition: If the quote violates these bounds, the transaction
reverts (atomicity).

10.3 Dynamic Trade Sizing

Trade size is not fixed at 15%. It is a function of liquidity:

TradeSize=min⁡(Deviation×Vgross, 0.10×PoolDepth24h)TradeSize=min(Deviation×Vgross​, 0.10×PoolDepth24h​)

This prevents the protocol from sliding the market.

11. Geopolitical Eject (Staged Liquidation) & Reintegration Score

11.1 The Detector (Peg Stability)

If an asset (e.g., EURC) trades outside the 0.98−1.020.98−1.02 band
for > 12 hours.

11.2 Staged Liquidation (Not 100%)

Instead of selling 100% instantly, the protocol executes a ladder:

  -----------------------------------------------------------------------
  Stage    Sell %      Condition
  -------- ----------- --------------------------------------------------
  1        10%         Depeg detected > 12h

  2        25%         Depeg > 24h OR RR < 1.08

  3        50%         Depeg > 48h OR RR < 1.05

  4        100%        Liquidity collapses OR issuer freeze confirmed
  -----------------------------------------------------------------------

Rule: Each stage executes only if the previous stage's sell did not
worsen the deviation.

11.3 Reintegration Score (Anti-Gaming)

The asset is re-purchased only when a score exceeds a threshold:

Rscore=w1⋅TimeInBand48h+w2⋅LiquidityDepth+w3⋅OracleAgreement+w4⋅(1−Volatility)Rscore​=w1​⋅TimeInBand48h​+w2​⋅LiquidityDepth+w3​⋅OracleAgreement+w4​⋅(1−Volatility)

If Rscore>0.80Rscore​>0.80, the protocol stages the re-purchase (25% →
50% → 100%).

16. Final Declaration

MTQ Σ v1.2 is a closed-loop monetary architecture.

-   The GFB Index (fixed currency quantities) defines the reference
    value.

-   The Reserve NAV collateralizes the token.

-   Minting is priced against the GFB Index, breaking the 1:1 USD peg.

-   Redemption is priced against NAV and releases the full proportional
    basket.

-   The Oracle, Eject, and Rebalancing engines are now mathematically
    consistent.

This is not yet production-authorized. It is a candidate for testnet
validation.

The GFB Index defines what one MTQ Σ is intended to represent. The
reserve portfolio exists to collateralize that obligation.

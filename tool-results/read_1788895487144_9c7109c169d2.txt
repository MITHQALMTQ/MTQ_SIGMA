     3→22.1 Constitutional Separation of the Algorithmic Layers
     4→
     5→  The architecture has three independent mathematical layers, and their
     6→  independence is constitutional: each layer is governed, validated and
     7→  audited separately, so that no single algorithm can silently control
     8→  the system [MS §90].
     9→
    10→  This prevents one algorithm from silently controlling everything.
    11→
    12→Layer 1 is the Constituency Engine, and it answers one question: who is
    13→eligible? (Chapter 4). Its domain is the candidate universe — which
    14→currencies and gold qualify for the active basket — decided by the
    15→eligibility score Q_i with entry and exit hysteresis. Its boundary is
    16→equally narrow: it may never assign a weight, execute a trade or hold an
    17→asset; it only admits and retires members. Layer 2 is MASE, the
    18→Multi-model Adaptive Stability Engine, and it answers the question: how
    19→much weight? (Chapters 5–7). Its domain is the target weight vector for
    20→the eligible members, produced by the ensemble under the composite
    21→objective. Its boundary: it weighs only what Layer 1 has admitted, and
    22→it never executes anything — its output is a target, not a trade. Layer
    23→3 is the MARP / Reserve Engine, and it answers the question: when and
    24→how do we execute? (Chapters 10–16). Its domain is execution decisions
    25→and reserve management. Its boundary: it moves toward Layer 2's targets,
    26→within Layer 1's membership, under the reserve rules — it never
    27→redefines the target or the membership. The summary table of Section 2.2
    28→carries the same three layers with their primary chapters.

    65→
    66→Independent governance means each layer has its own parameter classes in
    67→the parameter registry (Section 22.4), its own version stream (Section
    68→24.2) and its own validation tests in the research program (Chapter 23).
    69→Independent audit means each layer's outputs are reproducible from its
    70→own published inputs — an auditor can attribute any change in the live
    71→weight vector to exactly one layer (Section 2.2). The separation is also
    72→the containment strategy: a faulty optimizer cannot admit a broken
    73→currency, because Layer 1's eligibility gate stands in front of it; a
    74→faulty executor cannot chase a bad target, because MARP's justification
    75→gates (Chapter 10) stand between target and trade; and a compromised
    76→data feed cannot silently reweight the basket, because the oracle layer
    77→(Chapter 17) and the registry's envelope checks (Section 7.7) bound what
    78→any single input can do.
    79→
    80→22.2 Governance Separation
    81→
    82→Governance in MTQ Σ approves rules, never outcomes [MS §91]. The
    83→governance bodies may approve six categories of change:
    84→
    85→-   Methodology — the published, versioned methodology that defines how
    86→    weights are computed (Invariant I3); methodology changes are
    87→    constitutional and follow the 90-day process.
    88→
    89→-   Parameter envelopes — the admissible bounds within which tunable
    90→    parameters may move (Section 22.4); the envelope itself is
    91→    constitutional, while the value inside it follows the layer's own
    92→    path.
    93→
    94→-   Eligible data providers — which institutional and oracle sources may
    95→    feed the engines (Chapters 4 and 17).
    96→
    97→-   Eligible reserve instruments — which tokens and instruments may back
    98→    the unit (Chapter 15).
    99→
   100→-   Risk thresholds — the solvency, liquidity and eject thresholds of
   101→    Chapter 21.
   102→
   103→-   Emergency rules — the emergency action set and its authorization
   104→    (Sections 22.5–22.6).
   105→
   106→What no governance body may do — on any layer, under any quorum, in any
   107→state — is manually set an individual live weight on a discretionary
   108→basis [MS §91]:
   109→
   110→Governance → {rules} Governance not→ W_(USD,t), W_(Gold,t)
   111→
   112→This is Invariant I8 (Section 2.6): no governance body may set
   113→individual live weights by discretion. The prohibition is structural,
   114→not merely legalistic. Live weights enter the system through exactly one
   115→door — the MASE submission path of Section 7.7 — which verifies the data
   116→version, the methodology hash, the constitutional envelopes, the
   117→velocity limits and the smoothing rule before a vector can become live.
   118→To set a weight by hand, a governance body would have to counterfeit an
   119→entire data-and-methodology pipeline, in public, against a contract that
   120→checks every property it can verify on-chain. Discretionary weights
   121→would also destroy the two properties the unit is built on:
   122→reproducibility (Section 24.1 — an auditor could no longer re-derive the
   123→live vector from published inputs) and the fixed-methodology promise
   124→itself (Invariant I3).
   125→
   126→The boundary has a precise shape: governance can change the rules of the
   127→game — the methodology, the envelopes, the thresholds — but never the
   128→score of a particular game. A Risk Council that dislikes the live CHF
   129→weight may tighten the CHF envelope (a constitutional action),
   130→commission a methodology revision (also constitutional), or wait for the
   131→data to move; it may not type a number into the registry and make it
   132→live. This is what distinguishes an algorithmic monetary architecture
   133→from a managed one, and it is the reason Invariants I7 and I8 point at
   134→Sections 22.3 and 22.4 as their enforcement.
   135→

   173→
   174→Reading the table: Constitutional authority (a 7/7 Multi-Sig with a
   175→90-day timelock) covers the immutable core — the architecture, the
   176→constitutional envelopes, the hard floors, the fixed methodology and the
   177→liquidation ladder's shape. Monetary authority (DAO vote, 51% quorum,
   178→48-hour timelock) covers the monetary-policy parameters: the RR targets,
   179→the fee structure and the smoothing parameters. Risk authority (Risk
   180→Council, 4/7 with a 24-hour timelock) covers the technical risk
   181→parameters: haircuts, thresholds, eject parameters and LCR targets.
   182→Emergency authority (Emergency Council, 4/7, instant) covers only the
   183→pause/eject/rebalance action set of Section 22.5 — the one layer that
   184→trades deliberation for speed, and pays for it with the narrowest scope
   185→in the system.
   186→
   187→The layering implements Invariant I7 (Section 2.6): the protocol is
   188→governed by a layered hierarchy, and no layer can reach into another's
   189→domain. The timelocks themselves are constitutional (Section 22.4): the
   190→Emergency Council cannot shorten the monetary timelock, and the DAO
   191→cannot raise a constitutional change through a 51% vote. The councils
   192→are distinct bodies with distinct keys — the Risk Council and the
   193→Emergency Council operate separate 4/7 Multi-Sigs, both with hardware
   194→wallet requirements, so that compromising one signers set does not yield
   195→both authorities. Every action on every layer emits events and is
   196→published (Chapter 24); the layer boundaries are exactly what Invariants
   197→I7 and I8 reference from Section 2.6.

   199→22.4 The Parameter Registry and Authority Matrix
   200→
   201→Every tunable parameter in the protocol is registered — with its
   202→identifier, its governance layer, its current value and its admissible
   203→envelope — in a single on-chain parameter registry [BP §14.4.2]. The
   204→registry is the normative answer to the question of who may change what:
   205→an update path exists if and only if the parameter is registered, and
   206→the layer of the record determines which body, which quorum and which
   207→timelock govern the change. Unregistered parameters fail closed — the
   208→governance contract of Listing 14 reverts on any update to an unknown
   209→parameter identifier — so new parameters must be deliberately registered
   210→(a constitutional action) before they can ever be touched.
   211→
   212→-   Registration declares the parameter identifier, its layer
   213→    (Constitutional, Monetary, Risk or Emergency), its initial value and
   214→    its envelope in, max]; registration and envelope changes follow
   215→    the constitutional process with the 90-day timelock.
   216→
   217→-   Envelope discipline: proposed values must lie inside the registered
   218→    envelope at proposal time, and are re-checked at execution time and
   219→    again on arrival at the operations contract — three independent
   220→    checks, so a stale or manipulated proposal cannot bypass the bounds.
   221→
   222→-   Timelock discipline: monetary changes execute only after 48 hours,
   223→    risk changes only after 24 hours, and the Risk Council may veto a
   224→    monetary proposal inside its timelock window (Section 22.6).
   225→
   226→-   Audit trail: every registration, proposal, execution and veto emits
   227→    an event and is versioned with the data and methodology versions
   228→    (Section 24.2), so the complete parameter history is reconstructable
   229→    after the fact.

   357→22.5 Emergency Actions
   358→
   359→The Emergency layer holds the protocol's fastest powers, and every one
   360→of them is a verb — pause, force, eject, resume — rather than a setting
   361→[BP §14.5]. Emergency authority can never change a parameter, never set
   362→a weight and never amend the constitution; it can only halt or force the
   363→operations the state machine would otherwise run:
   364→
   365→  --------------------------------------------------------------------------
   366→  Action               Description       Trigger           Authority
   367→  -------------------- ----------------- ----------------- -----------------
   368→  pauseMinting()       Stops all new     RR < 1.05         Automatic +
   369→                       minting           (automatic) OR    Council
   370→                                         Council decision  
   371→
   372→  pauseRedeeming()     Stops all         EMERGENCY state + Council (4/7)
   373→                       redemptions       Council vote      
   374→                       (extreme cases                      
   375→                       only)                               
   376→
   377→  forceRebalance()     Executes an       EMERGENCY state   Council (4/7)
   378→                       immediate                           
   379→                       rebalance                           
   380→
   381→  emergencyEject()     Immediately       Issuer freeze     Council (4/7)
   382→                       ejects a          confirmed         
   383→                       de-pegged asset                     
   384→
   385→  resumeOperations()   Restores normal   Recovery          Council (4/7)
   386→                       operations        confirmed         
   387→  --------------------------------------------------------------------------
   388→
   389→The trigger column shows the two-speed design. The first pause — minting
   390→at RR < 1.05 — is automatic: the state machine applies it the moment
   391→STRESS is entered (Section 21.4), so the protocol's first defensive move
   392→does not wait for humans. The remaining actions are council-triggered,
   393→because they trade user-facing continuity against risk in ways that
   394→require judgment. Pausing redemptions is the most drastic user-facing
   395→action in the system and requires the EMERGENCY state plus a council
   396→vote. A forced rebalance is a discretionary override of the MARP
   397→doctrine's justification gates and corresponds to Level 5 of the
   398→execution hierarchy (Section 10.3). The emergency eject bypasses the
   399→staged liquidation ladder and executes through emergencyLiquidate
   400→(Section 21.6) when an issuer freeze is confirmed. And resumeOperations
   401→is deliberately blocked while the state machine is still in EMERGENCY:
   402→recovery, not decree, must end an existential state.
   403→
   404→Checks and balances. Every emergency action requires the 4/7 Emergency
   405→Council Multi-Sig with hardware wallet requirements, emits an on-chain
   406→event, and is reported through the transparency layer (Chapter 24) and
   407→the honest-status declaration (Section 25). The oracle layer's circuit
   408→breakers (Chapter 17) engage automatically in EMERGENCY, so price-trust
   409→failures and solvency failures brake together. The state machine
   410→continues to run underneath the council's actions: an emergency pause
   411→does not freeze RR/LCR reporting, state transitions or the recovery
   412→clock, so the council cannot use a pause to obscure the condition it is
   413→pausing about. Emergency power, in short, is instant but narrow,
   414→recorded, and reversible only by recovery — the exact trade the
   415→four-layer hierarchy of Section 22.3 is designed to force.

   417→22.6 Smart Contract Implementation — Governance and Emergency Functions
   418→
   419→The governance registry is the authorization plane of the protocol [BP
   420→§14.6.4–14.6.5]. It owns the parameter registry and the proposal flow:
   421→the DAO proposes and executes monetary changes across a 48-hour
   422→timelock, the Risk Council owns the 24-hour risk path and holds a veto
   423→over monetary proposals inside their window, the Constitutional Council
   424→registers parameters and their envelopes, and the Emergency Council
   425→dispatches the pause, force and resume actions of Section 22.5. Every
   426→executed update is forwarded to the operations contract of Listing 13
   427→through the IOperations interface, and the operations contract
   428→re-verifies its caller before applying the value — authorization and
   429→execution each check the other. The emergency eject is the single
   430→exception to the dispatch pattern: emergencyLiquidate is signed directly
   431→by the Emergency Council on the operations contract (Section 21.6),
   432→exactly as in the source module. The onlyDAO modifier is implemented by
   433→a DAO contract with 51% quorum, and the emergency modifier by a 4/7
   434→Multi-Sig with hardware wallet requirements [BP §14].

   578→  /// @dev Registers a tunable parameter with its governance class and
   579→
   580→  /// admissible envelope. Unregistered parameters cannot be updated

   582→  /// (fail-closed). Envelope changes are constitutional actions with
   583→
   584→  /// the 90-day timelock enforced by the multi-sig process.

   586→  function registerParameter(
   587→
   588→  bytes32 parameterId,
   589→
   590→  ParameterLayer layer,
   591→
   592→  uint256 value,
   593→
   594→  uint256 minValue,
   595→
   596→  uint256 maxValue
   597→
   598→  ) external onlyConstitutionalCouncil {
   599→
   600→  require(minValue <= value && value <= maxValue, "Value outside
   601→  envelope");
   602→
   603→  parameterRegistry[parameterId] = ParameterRecord({
   604→
   605→  layer: layer,
   606→
   607→  value: value,
   608→
   609→  minValue: minValue,
   610→
   611→  maxValue: maxValue,
   612→
   613→  registered: true
   614→
   615→  });
   616→
   617→  emit ParameterRegistered(parameterId, layer, value, minValue,
   618→  maxValue, block.timestamp);
   619→
   620→  }

   628→  /// @dev Proposes a monetary parameter change (DAO).
   629→
   630→  function proposeMonetaryParameter(bytes32 parameterId, uint256
   631→  newValue) external onlyDAO {
   632→
   633→  require(parameterRegistry[parameterId].registered, "Unknown
   634→  parameter");
   635→
   636→  require(parameterRegistry[parameterId].layer ==
   637→  ParameterLayer.MONETARY, "Not a monetary parameter");
   638→
   639→  require(newValue >= parameterRegistry[parameterId].minValue, "Below
   640→  envelope");
   641→
   642→  require(newValue <= parameterRegistry[parameterId].maxValue, "Above
   643→  envelope");
   644→
   645→  proposals[parameterId] = Proposal({
   646→
   647→  value: newValue,
   648→
   649→  proposer: msg.sender,
   650→
   651→  timestamp: block.timestamp,
   652→
   653→  executed: false
   654→
   655→  });
   656→
   657→  emit ParameterProposed(parameterId, newValue, block.timestamp);
   658→
   659→  }
   660→
   661→  /// @dev Executes a monetary parameter change after the 48h timelock.
   662→
   663→  function executeMonetaryParameter(bytes32 parameterId) external
   664→  onlyDAO {
   665→
   666→  Proposal memory proposal = proposals[parameterId];
   667→
   668→  require(proposal.timestamp > 0, "No proposal");
   669→
   670→  require(block.timestamp >= proposal.timestamp + TIMELOCK_MONETARY,
   671→  "Timelock not met");
   672→
   673→  require(!proposal.executed, "Already executed");
   674→
   675→  // Update the parameter
   676→
   677→  updateParameter(parameterId, proposal.value);
   678→
   679→  proposals[parameterId].executed = true;
   680→
   681→  emit ParameterExecuted(parameterId, proposal.value, block.timestamp);
   682→
   683→  }
   684→
   685→  /// @dev Vetoes a monetary parameter change (Risk Council, within the
   686→
   687→  /// timelock window).
   688→
   689→  function vetoMonetaryParameter(bytes32 parameterId) external
   690→  onlyRiskCouncil {
   691→
   692→  require(proposals[parameterId].timestamp > 0, "No proposal");
   693→
   694→  require(block.timestamp < proposals[parameterId].timestamp +
   695→  TIMELOCK_MONETARY, "Timelock expired");
   696→
   697→  delete proposals[parameterId];
   698→
   699→  emit ParameterVetoed(parameterId, block.timestamp);
   700→
   701→  }

   770→  /// @dev Writes the accepted value to the registry and forwards it to
   771→  the
   772→

   777→  function updateParameter(bytes32 parameterId, uint256 newValue)
   778→  internal {
   779→

   785→  "Outside envelope");

   788→

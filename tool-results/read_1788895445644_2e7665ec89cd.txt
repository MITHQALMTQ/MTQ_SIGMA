    12→## Executive Summary
    13→
    14→`MTQSigmaV2.sol` is a single-file, no-import, direct-deploy ERC-20 that
    15→attempts to put the MTQΣ Master Monetary Architecture v1.0 on-chain. The
    16→ERC-20 core, the inline AccessControl + Pausable, the multi-source oracle
    17→adapter with §9.2/§9.3 consensus, the per-component admissibility envelopes,
    18→and the §14.1 risk state machine are implemented faithfully and compile
    19→cleanly under solc 0.8.20 (one Spurious Dragon size warning — must deploy
    20→with optimizer runs=200, per the manifest). However, the contract
    21→**overstates its own `0x7FF` honest-status mask**: 4 of the 11 bits
    22→(`chainLinkedIndex`, `maseWeightRegistry`, `marpExecution`,
    23→`daoGovernance`) describe features that are only partially implemented.
    24→The two most material blueprint divergences are (i) the GFB index uses
    25→the immutable *Strategic Prior* weights for every `getGFB()` call — the
    26→MASE-committed `targetWeights / smoothedWeights / executionWeights` are
    27→stored but **never consumed** by pricing; and (ii) the "chain-linked
    28→index" is a fixed-base index (one immutable denominator), not the
    29→recursive `I_t = I_{t-1} × Σ W_{i,t-1}·(P_{i,t}/P_{i,t-1})` form mandated
    30→by §9.2/§9.3. There is also a missing §11.5.3 RR<1.05 override on the
    31→rebalance direction lock (a solvency hazard under stress), one
    32→reentrancy-ordering issue in `mint()` (CEI violated), one genesis
    33→lock-out vector (`genesisMint(0)`), one reserve-mirror wipe vector
    34→(`bootstrapReserveHoldings` is re-callable), an unbounded `executeRebalance`
    35→loop (gas DoS), and a 2-colluding-oracle price-pin vector (no per-pair
    36→price floor). The DAO timelock implements only **one** of the four
    37→governance layers required by §22.3 (Monetary 48h; missing Constitutional
    38→90d, Risk 24h, Emergency instant). The contract is **NOT** production-
    39→authorized in its current form — 6 critical/high findings must be
    40→remediated, and the `0x7FF` mask should be reduced to `0x5A7` (or the
    41→missing features actually implemented) before the on-chain self-
    42→declaration can be called honest.

   102→### C1 — MASE weights are committed but never consumed by `getGFB()`
   103→
   104→```solidity
   105→// Lines 420–431 — getGFB() uses immutable Strategic Prior weights
   106→function getGFB() public view returns (uint256) {
   107→    uint256 numerator = (
   108→          PRIOR_USD                          // ← immutable constant
   109→        + PRIOR_EUR * fxEUR_USD / 1e18        // ← immutable constant
   110→        + PRIOR_JPY * fxJPY_USD / 1e18
   111→        + PRIOR_GBP * fxGBP_USD / 1e18
   112→        + PRIOR_CNY * fxCNY_USD / 1e18
   113→        + PRIOR_CHF * fxCHF_USD / 1e18
   114→        + PRIOR_GOLD * fxXAU_USD / 1e18
   115→    );
   116→    return numerator * 1e18 / GFB_BASE_DENOMINATOR;
   117→}
   118→
   119→// Lines 560–576 — commitWeights stores target/smoothed/execution weights…
   120→function commitWeights(uint256[7] calldata target, uint256[7] calldata smoothed, uint256[7] calldata execution)
   121→    external onlyOracleOrKeeper {
   122→    for (uint8 i = 0; i < 7; i++) {
   123→        Component c = Component(i);
   124→        _assertEnvelope(c, target[i]);
   125→        _assertEnvelope(c, smoothed[i]);
   126→        _assertEnvelope(c, execution[i]);
   127→        weights.targetWeights[i]    = target[i];
   128→        weights.smoothedWeights[i] = smoothed[i];
   129→        weights.executionWeights[i] = execution[i];
   130→    }
   131→    weights.lastUpdatedAt = block.timestamp;
   132→    emit WeightsCommitted(target, smoothed, execution, block.timestamp);
   133→}
   134→```
   135→
   136→**Impact.** The blueprint's central thesis (§2.6 I3, §7, §8.1, §24 I6)
   137→is that the published weight `W_t` is always the *execution* weight
   138→produced by the MASE ensemble, not the immutable Strategic Prior. The
   139→contract's `getGFB()` — which is also `getMTQPrice()` (line 436–438) —
   140→ignores `weights.executionWeights` entirely. Minting and redemption
   141→(line 470, 502) therefore settle against a *fixed-weight* index, while
   142→the MASE registry is a cosmetic side-store. This breaks the central
   143→monetary claim of v1.0 ("adaptive composition, not fixed weights") and
   144→means bit 4 of `getHonestStatus()` is dishonest.
   145→
   146→**Recommendation.** Either (a) re-write `getGFB()` to consume
   147→`weights.executionWeights` (with a fallback to `PRIOR_*` before the first
   148→`commitWeights`), or (b) reduce bit 4 in the honest-status mask until
   149→the consumption is wired. Option (a) is the blueprint-correct path.

   153→### C2 — "Chain-linked index" is a fixed-base index (no recursive `I_t = I_{t-1} × …`)
   154→
   155→```solidity
   156→// Line 182
   157→uint256 public immutable GFB_BASE_DENOMINATOR;
   158→
   159→// Lines 364–372 — denominator computed ONCE in the constructor
   160→GFB_BASE_DENOMINATOR = (
   161→      PRIOR_USD
   162→    + PRIOR_EUR * BASE_EUR_USD / 1e18
   163→    + PRIOR_JPY * BASE_JPY_USD / 1e18
   164→    + PRIOR_GBP * BASE_GBP_USD / 1e18
   165→    + PRIOR_CNY * BASE_CNY_USD / 1e18
   166→    + PRIOR_CHF * BASE_CHF_USD / 1e18
   167→    + PRIOR_GOLD * BASE_XAU_USD / 1e18
   168→);
   169→```
   170→
   171→The blueprint (§9.2/§9.3, and the canonical Listing at
   172→blueprint-v1.0.txt lines 4090–4140) specifies a recursive index:
   173→
   174→```text
   175→I_t = I_{t-1} × Σ_i W_{i,t-1} × (P_{i,t} / P_{i,t-1})
   176→```
   177→
   178→with a `chainLinkDivisor` (cumulative product of `D_t`) that preserves
   179→continuity across weight changes. The contract has no `updateIndex()`,
   180→no `lastPrices`, no `lastWeights`, no `chainLinkDivisor`. Each
   181→`getGFB()` call divides the live numerator (computed from current FX
   182→rates and **fixed Strategic Prior weights**) by the immutable base
   183→denominator. This is a Laspeyres-style fixed-base index, not a
   184→chain-linked index. Constituency changes (§4.6), methodology versions
   185→(§22.3 Constitutional), and weight changes (§7.7) cannot be reflected
   186→without breaking index continuity — exactly the failure mode
   187→chain-linking was designed to prevent.
   188→
   189→**Impact.** Bit 3 of `getHonestStatus()` (`chainLinkedIndex`) is
   190→overstated. Worse, the on-chain price cannot evolve correctly when
   191→MASE eventually changes weights (cf. C1) — even if C1 is fixed, the
   192→price will jump discontinuously at every weight change because there
   193→is no `D_t` continuity adjustment.
   194→
   195→**Recommendation.** Implement the recursive advance: store
   196→`lastPrices[7]`, `lastWeights[7]`, `chainLinkDivisor`; add an
   197→`updateIndex()` keeper call (daily cadence per §10.1) that computes
   198→`indexValue = indexValue * growth / 1e18` where
   199→`growth = Σ lastWeights[i] * P[i] / lastPrices[i]`. Until then,
   200→drop bit 3.

   204→### C3 — DAO governance implements only 1 of 4 layers
   205→
   206→```solidity
   207→// Lines 300–324 — single 48h timelock, single admin role
   208→uint256 public constant TIMELOCK_DELAY = 48 hours; // §5.10 / §14.2 monetary tier
   209→
   210→struct ParameterChange {
   211→    bytes32  key;
   212→    uint256  newValue;
   213→    uint256  queuedAt;
   214→    uint256  executesAt;
   215→    bool     executed;
   216→}
   217→mapping(bytes32 => ParameterChange) public paramChanges;
   218→
   219→bytes32 public constant PARAM_MINT_FEE_BPS         = keccak256("PARAM_MINT_FEE_BPS");
   220→bytes32 public constant PARAM_REDEEM_FEE_BPS       = keccak256("PARAM_REDEEM_FEE_BPS");
   221→bytes32 public constant PARAM_RESERVE_RATIO_TARGET = keccak256("PARAM_RESERVE_RATIO_TARGET");
   222→```
   223→
   224→The blueprint (§22.3, line 16703–16752 of blueprint-v1.0.txt) defines
   225→**four** distinct governance bodies:
   226→
   227→| Layer | Authority | Timelock | Scope |
   228→|-------|-----------|----------|-------|
   229→| Constitutional | 7/7 Multi-Sig | 90 days | Envelopes, hard floors, methodology |
   230→| Monetary | DAO 51% | 48h | RR target, fees, smoothing |
   231→| Risk | Risk Council 4/7 | 24h | Haircuts, thresholds, eject |
   232→| Emergency | Emergency Council 4/7 | instant | Pause, force-rebalance, eject |
   233→
   234→The contract has a single 48h timelock and a single `ADMIN_ROLE`. Haircuts
   235→are not even a settable parameter (they come from the external
   236→`IAssetRegistry`, but the registry address is set by `ADMIN_ROLE` with no
   237→timelock at all — line 837–840, `onlyAdmin`). There is no on-chain
   238→enforcement of 4/7 multisigs — those are an off-chain operational
   239→assumption. There is no way to change envelopes (correct — they are
   240→immutable) but there is also no way to change haircuts, LCR targets, or
   241→eject parameters through any governance path.
   242→
   243→**Impact.** Bit 9 of `getHonestStatus()` (`daoGovernance`) is overstated.
   244→The contract has a *Monetary-tier timelock* — that is one of the four
   245→layers, not all four.
   246→
   247→**Recommendation.** Either (a) implement a `RiskCouncil` role with a
   248→24h timelock for haircuts/eject params, an `EmergencyCouncil` role for
   249→instant pause (already partly present as `PAUSER_ROLE` but no
   250→multisig/quorum enforcement), and document the 90d Constitutional path
   251→as "deploy a new contract"; or (b) drop bit 9 until all four layers are
   252→on-chain.

   256→### C4 — `executeRebalance` missing §11.5.3 RR<1.05 direction-lock override
   257→
   258→```solidity
   259→// Lines 624–631 — direction lock with NO override
   260→int256 prevDir = lastDirection[t.component];
   261→if (prevDir != 0 && prevDir != t.direction) {
   262→    require(
   263→        block.timestamp >= lastRebalanceAt[t.component] + DIRECTION_LOCK_HOURS,
   264→        "MTQV2: direction lock"
   265→    );
   266→}
   267→```
   268→
   269→The blueprint (§11.5.3, blueprint-v1.0.txt lines 5209–5215) is explicit:
   270→*"The direction lock is overridden if the reserve ratio drops below 1.05
   271→(Stress Mode). In that case the engine may reverse direction regardless
   272→of the lock to protect solvency — solvency outranks anti-churn."*
   273→
   274→**Impact.** If the protocol sells Gold on day 1 (RR=1.10) and the next
   275→day RR collapses to 1.02 (below hard floor) and the only correct action
   276→is to *buy* Gold back, the contract reverts with `"MTQV2: direction
   277→lock"` and the protocol is trapped away from its target during the
   278→exact window where it most needs to correct. This is a solvency hazard,
   279→not just a blueprint-conformance gap.
   280→
   281→**Recommendation.** Add at line 626:
   282→```solidity
   283→if (prevDir != 0 && prevDir != t.direction) {
   284→    // §11.5.3 solvency override
   285→    if (getReserveRatio() >= 1.05e18) {
   286→        require(
   287→            block.timestamp >= lastRebalanceAt[t.component] + DIRECTION_LOCK_HOURS,

   402→### H1 — `mint()` violates Checks-Effects-Interactions
   403→
   404→```solidity
   405→// Lines 463–490 (abbreviated)
   406→function mint(uint256 usdcAmount) external whenNotPaused returns (uint256 minted) {
   407→    require(usdcAmount > 0, "MTQV2: zero amount");
   408→    require(protocolStatus != Status.DEFENSIVE && protocolStatus != Status.EMERGENCY, …);
   409→    uint256 price = getMTQPriceWithGuard();
   410→
   411→    // INTERACTION — external call BEFORE the state effect (_mint)
   412→    require(usdc.transferFrom(msg.sender, reserveVault, usdcAmount), "MTQV2: USDC pull failed");
   413→
   414→    uint256 feeUsd = usdcAmount * mintFeeBps / 10000;
   415→    uint256 netUsd = usdcAmount - feeUsd;
   416→    uint256 netUsd18  = netUsd * 1e12;
   417→    uint256 grossMint = netUsd18 * 1e18 / price;
   418→    uint256 throttle = 1e18;
   419→    if (protocolStatus == Status.CAUTION)  throttle = 0.50e18;
   420→    if (protocolStatus == Status.RECOVERY) throttle = 0.25e18;
   421→    minted = grossMint * throttle / 1e18;
   422→
   423→    // EFFECT — _mint AFTER the external call
   424→    _mint(msg.sender, minted);
   425→    emit Mint(msg.sender, usdcAmount, feeUsd, minted, price);
   426→}
   427→```
   428→
   429→**Impact.** Standard USDC has no transfer hooks, so under the
   430→manifest's intended deployment (USDC at `0x334D14E7E39e1f02a60fc1169CdF7b0BEDE30dEb`
   431→on Arc) this is safe. But the constructor takes an arbitrary `_usdc`
   432→address (line 347/359), and the contract has no `nonReentrant` modifier.
   433→If `_usdc` is ever set to an ERC-777 / ERC-1363 / malicious token (e.g.,
   434→a future migration to a yield-bearing USDC variant), `transferFrom`
   435→will call back into `mint()` before `_mint` runs. Re-entered calls are
   436→bounded by the user's USDC allowance, so the attacker cannot mint more
   437→MTQ than their deposited USDC — but they can trigger multiple `Mint`
   438→events and confuse off-chain accounting.
   439→
   440→`redeem()` (lines 498–518) does the opposite — `_burn` (line 514)
   441→before `usdc.transferFrom` (line 516) — so it follows CEI for the MTQ
   442→side; but `transferFrom(reserveVault, msg.sender, …)` where
   443→`msg.sender` is a contract can still trigger a hook on receipt, and
   444→re-entering `redeem()` would fail the `balanceOf` check (already
   445→burned). So `redeem()` is safe by construction; `mint()` is not.
   446→
   447→**Recommendation.** Either (a) follow strict CEI: compute `minted`
   448→first, call `_mint(msg.sender, minted)`, then call
   449→`usdc.transferFrom(…)` — but this requires the user to pre-approve a
   450→*different* amount (since `minted` is denominated in MTQ, not USDC),
   451→which breaks the current UX. Better: (b) add an OZ-style
   452→`nonReentrant` modifier on `mint()` and `redeem()`:
   453→```solidity
   454→modifier nonReentrant() {
   455→    require(!_locked, "MTQV2: reentrant"); _locked = true; _; _locked = false;
   456→}
   457→```
   458→And/or (c) whitelist the USDC implementation at construction (check
   459→`usdc.symbol()` keccak256 == "USDC" keccak256, or check the codehash).

   564→```solidity

   777→}
   778→
   779→// Line 617
   780→require(t.level >= 1 && t.level <= 6, "MTQV2: invalid MARP level");
   781→```
   782→
   783→The blueprint §10.3 defines a 6-level hierarchy (Levels 0–5):
   784→Monitor, Natural Flow, Drift Trigger, Risk Trigger, Structural Change,
   785→Emergency. Each level has a *trigger* (deviation threshold, risk
   786→deterioration, RR stress, etc.) and a *response* (no trade, natural
   787→flow, partial correction, staged correction, ramped reallocation,
   788→crisis mode). The contract accepts `level` as a free input from the
   789→keeper — it just validates the range. There is no on-chain check that
   790→the level matches the actual trigger conditions; no Level 5 → crisis
   791→mode transition (which §13.7 says should widen no-trade bands, shrink
   792→sizes, raise liquidity requirements); no Level 4 → ramped execution;
   793→no Level 1 → "natural flow first" accounting. The contract also
   794→encodes levels as 1–6 instead of the blueprint's 0–5 — off by one.
   795→
   796→**Impact.** Bit 6 (`marpExecution`) is partial: the *execution engine*
   797→exists (direction lock, daily cap, tolerance, reserve mirror), but
   798→the *6-level hierarchy* — which is the intellectual core of MARP — is
   799→not on-chain. The keeper simply declares "this is a Level 3 trade"
   800→and the contract trusts it.
   801→
   802→**Recommendation.** Either (a) implement the 6-level trigger checks
   803→on-chain (compute deviation, RR, crisis score per §5.5; validate the
   804→declared level matches), or (b) reduce bit 6 to "marpExecutionEngine"
   805→and document that the hierarchy is off-chain. Also fix the level
   806→encoding (0–5 not 1–6).

   917→### M7 — `queueChange` can be re-queued, resetting the 48h timelock
   918→
   919→```solidity
   920→// Lines 901–910
   921→function queueChange(bytes32 key, uint256 newValue) external onlyAdmin {
   922→    ParameterChange storage pc = paramChanges[key];
   923→    require(!pc.executed, "MTQV2: already executed");   // ← only blocks if executed
   924→    pc.key        = key;
   925→    pc.newValue   = newValue;
   926→    pc.queuedAt   = block.timestamp;
   927→    pc.executesAt = block.timestamp + TIMELOCK_DELAY;   // ← timer reset
   928→    pc.executed   = false;
   929→    emit ParameterQueued(key, newValue, pc.executesAt);
   930→}
   931→```
   932→
   933→If a parameter is queued (not executed), a second `queueChange` with
   934→the same key overwrites `newValue` AND resets `executesAt` to
   935→`block.timestamp + 48h`. An admin can indefinitely delay an already-
   936→queued change by re-queuing with the same value (griefing), or
   937→bait-and-switch a queued value (the `ParameterQueued` event emits the
   938→new value at the new executesAt, so it's auditable, but it's a
   939→control-flow surprise for watchers expecting monotonic timelock
   940→advance).
   941→
   942→**Recommendation.** Either (a) `require(pc.queuedAt == 0 ||
   943→pc.executed, "MTQV2: already queued — cancel first")` (force a
   944→cancel-then-re-queue pattern), or (b) keep the existing overwrite
   945→behavior but document it as "the timelock restarts on re-queue."

   973→
   974→### Genesis distribution
   975→- The contract does **not** enforce the blueprint's "1,000,000 MTQ @
   976→  1,100,000 USDC ⇒ RR = 1.10" convention. `genesisMint(amount)` (line
   977→  953) accepts any `amount` (including 0 — see C5), with no
   978→  collateral-backing check (see H7). The tokenomics are entirely
   979→  trust-based at genesis.
   980→- `genesisReserveBalance` (line 330) is set to `amount`, and
   981→  `getCirculatingSupply()` (line 448–450) correctly excludes it:
   982→  `totalSupply - genesisReserveBalance`. ✓
   983→- `genesisReserve` defaults to `address(this)` (line 361) — the
   984→  contract self-holds the genesis reserve. `setGenesisReserve(g)`
   985→  (line 961) allows moving it, with `g != address(0)` check. ✓
   986→
   987→### Fee model
   988→- `mintFeeBps = 10` (0.10%) at line 205 — matches §19.2. ✓
   989→- `redeemFeeBps = 15` (0.15% NORMAL/CAUTION) at line 206 — matches §3.4.2. ✓
   990→- DEFENSIVE 0.5% (50 bps) and EMERGENCY 2% (200 bps) at lines 506–507 —
   991→  match §14.1 RISK_STATE_MACHINE. ✓ But hardcoded (M8).
   992→- **Where do fees accrue?** `mint()` transfers the full `usdcAmount`
   993→  (including the fee) to `reserveVault` (line 473). `netUsd =
   994→  usdcAmount - feeUsd` (line 477) is only used to compute `minted`.
   995→  The fee is *not* separated — it sits in `reserveVault` alongside
   996→  the collateral. Per §20.4, fees should accrue to a separate
   997→  **Operational Wallet** (hot, sweepable to Cold Treasury per §13.4)
   998→  and be *excluded* from RR (per the critical rule at
   999→  blueprint-v1.0.txt line 14178: "assets in the Operational Wallet and
  1000→  Cold Treasury are not counted toward the Reserve Ratio"). The
  1001→  contract commingles them — fees silently inflate the apparent RR.
  1002→  This is L5.
  1003→
  1004→### Inflation / Burn
  1005→- No inflation. `_mint` is only called from `mint()` (deposit-backed)
  1006→  and `genesisMint()` (one-shot). ✓
  1007→- `redeem()` calls `_burn(msg.sender, mtqAmount)` (line 514) — MTQ is
  1008→  burned on redemption. ✓
  1009→- No max-supply cap. Per blueprint (supply grows with deposits) —
  1010→  intentional (L3).
  1011→
  1012→### Circulating supply & market cap
  1013→- `getCirculatingSupply() = totalSupply - genesisReserveBalance` (line
  1014→  448–450). ✓
  1015→- MTQ price = GFB index (line 436–438). With base FX rates at
  1016→  constructor time, `getGFB()` returns 1.0e18 (numerator = denominator,
  1017→  both using base fixings). After live FX updates (or oracle commit),
  1018→  price moves. With current FX (per the pilot app's feed), price ≈
  1019→  $1.76.
  1020→- Initial market cap = circulatingSupply × price. With 0 circulating
  1021→  (genesis only, locked), market cap = $0 until users mint. ✓ This
  1022→  matches the blueprint's intent — no market cap until deposits.
  1023→
  1024→### Honest market cap implication
  1025→- With 1M MTQ at genesis (locked, excluded from circulating) and 0
  1026→  user deposits, circulatingSupply = 0, market cap = $0. The protocol
  1027→  is "pre-launch" until the first user mint. This is honest — but the
  1028→  contract does not enforce the 1M / 1.1M USDC convention, so a
  1029→  misconfigured deploy could mint 100M MTQ with 0 USDC and the
  1030→  on-chain RR computation would not flag it until the first user
  1031→  interaction. See H7.
  1032→
  1033→### Reserve accounting
  1034→- `getReserveNavUsd()` (line 843–849) sums `reserveHeldUsd[]` — a
  1035→  manual mirror that must be bootstrapped via
  1036→  `bootstrapReserveHoldings` (line 974) and maintained via
  1037→  `setReserveHolding` (line 981) and `executeRebalance` (line 657). The
  1038→  contract does **not** read actual token balances from the vault —
  1039→  it trusts the mirror. A misconfigured mirror silently corrupts NAV
  1040→  and RR (see H4).
  1041→- `getReserveNetAssetValue()` (line 855–884) applies §14.1 haircuts
  1042→  via `IAssetRegistry`, with frozen/delisted assets contributing 0. ✓
  1043→  Falls back to gross sum if the registry is unset (line 856–858) — a
  1044→  graceful-degrade path that means bit 7 is *conditional* on a wired
  1045→  registry.
  1046→
  1047→### Reserve ratio
  1048→- `getReserveRatio()` (line 888–893) = net NAV / liability. ✓
  1049→- Returns `type(uint256).max` if `liab == 0` (line 891) — i.e., before
  1050→  any user mint, RR = ∞. This is a graceful-degrade but can mask
  1051→  insolvency: a corrupted reserve mirror (H4) that zeroes `nav` while
  1052→  `liab > 0` would return `0`, which is below the hard floor — but
  1053→  there is **no on-chain action** triggered by RR < 1.00. The protocol
  1054→  does not auto-pause, auto-enter EMERGENCY, or auto-eject on RR
  1055→  breach. The blueprint's Invariant I2 ("RR_t ≥ 1.00 at all times") is
  1056→  enforced by *operator vigilance*, not by the contract.

  1080→
  1081→**Of the 11 bits claimed:**
  1082→- **7 are TRULY implemented** (bits 0, 1, 2, 5, 7, 8, 10) — the
  1083→  interface/scaffolding for these features is genuinely present.
  1084→- **4 are OVERSTATED** (bits 3, 4, 6, 9) — the bits are set in the
  1085→  mask but the underlying features are only partially implemented:
  1086→  - bit 3 `chainLinkedIndex`: fixed-base, not recursive.
  1087→  - bit 4 `maseWeightRegistry`: stored but not consumed by pricing.
  1088→  - bit 6 `marpExecution`: execution engine present but 6-level
  1089→    hierarchy missing, RR<1.05 override missing.
  1090→  - bit 9 `daoGovernance`: 1 of 4 governance layers implemented.
  1091→
  1092→**Honest mask would be:** clear bits 3, 4, 6, 9 from 0x7FF.
  1093→- Bits to clear: `(1<<3) | (1<<4) | (1<<6) | (1<<9)` = `0x008 | 0x010 | 0x040 | 0x200` = `0x258`.
  1094→- `0x7FF & ~0x258 = 0x7FF & 0x7A7 = 0x5A7`.
  1095→- Binary: `0b10110100111` — bits 0, 1, 2, 5, 7, 8, 10 set. = **`0x5A7`** (decimal 1447).
  1096→

  1098→registry/adapters are actually wired at deploy time" interpretation
  1099→(which is conservative but defensible — bits 7 and 8 clear until the
  1100→manifest's post-deploy steps 7 and 8 are completed), the honest mask
  1101→drops further to `0x427` (bits 0, 1, 2, 5, 10 only).
  1102→

  1104→(conservative) to **6 bits** (strict). The contract is more honest
  1105→than the v1.2 pilot (which returns `0x400`, only bit 10), but it
